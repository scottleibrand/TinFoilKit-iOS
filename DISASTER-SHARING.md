# Nearby sharing after a disaster

After a major earthquake, cellular service may still be good enough to install an app while too congested for multi-gigabyte downloads. A household, library, or response team that already has Tinfoil Kit content should be able to pass it to someone nearby. The recipient should be able to read it offline immediately after verification, search it as indexing progresses, and offer it to someone else with fresh approval. The transfer must work after the towers and local internet go down.

## First-launch experience

1. Open a lightweight Tinfoil Kit install with a small, attributed, offline-readable starting reference and clear entry points for **Find nearby** and **Offer content**. Reuse the same app with two distribution build profiles, starting by excluding compiled regional data and optional routing packs from the lightweight profile. Keep the full offline features available as their data arrives. The current local device debug bundle is around 260 MB on disk with maps and a routing pack. Measure a thinned release archive by device class, with a provisional target of 30 MB compressed and a starter reference budget of 2 MB. Keep Seattle test fixtures in the development build and measure their size separately.
2. With Nearby open and local-network permission granted, automatically discover other Tinfoil Kit users whose Nearby screen is active. Show an ephemeral name and a way to identify the person in front of you. Support a generic request for an essential category or a named public catalog pack so a new user can ask for something without inspecting another device.
3. Select one or more items, see what will leave your device, and approve an offer to the intended peer. The recipient can review the offered set, size, provenance and storage cost, then accept or decline. The same flow covers a 50 KB guide and a multi-gigabyte archive.
4. Install and open verified items as they finish. Prioritize small local essentials such as emergency references and publisher-verified local information, then map coverage, routing, and large references. Show waiting, interrupted, verifying and indexing states, including remaining bytes and the option to cancel.

## Discovery and consent

- Use Network.framework with Bonjour and Apple peer-to-peer Wi-Fi, enabled explicitly, as the first transport for the current iOS 17 minimum. Declare the Nearby service and reuse the OS local-network permission flow. Test both a shared LAN with no internet and a direct link with no access point. Keep the existing browser-based household share separate from this protocol. [Apple Wi-Fi overview](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview) · [Apple networking guidance](https://developer.apple.com/documentation/Technotes/tn3151-choosing-the-right-networking-api)
- Evaluate Wi-Fi Aware as a second transport on iOS 26 and supported devices. Prototype two iPhones, the entitlement and System UI pairing before committing to it. Use the same content and consent protocol across transports. Keep the session foreground-first for initial release. Persist verified transfer checkpoints so leaving range, locking the phone or relaunching need only interrupt the session. [Apple Wi-Fi Aware adoption](https://developer.apple.com/documentation/wifiaware/adopting-wi-fi-aware) · [Apple pairing documentation](https://developer.apple.com/documentation/WiFiAware/Connecting-paired-devices)
- Advertise only a short-lived random identifier and protocol version. Never put names from Contacts, location, inventories, titles, digests, library holdings, or Ask history in discovery. Stop advertising and browsing when the Nearby screen closes. Apply local connection limits and timeouts, and use a transport bound to the local link so a fetch cannot spill onto cellular or fall back to an internet host.
- Authenticate the other device before revealing any offer. Prototype Network.framework TLS with both endpoints' keys verified through an in-person QR exchange. Gate the offer channel on that verification. An unverified connection can only negotiate protocol and pairing. Reuse approved transport primitives and have the protocol, storage parsers and consent flow reviewed before release. [Apple peer networking and TLS guidance](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework)
- Require an explicit sender action for every offer, including the offer metadata. Bind approval to the recipient, exact content digests and selected fields. Ask the recipient to accept before sending bytes. Pairing, being on the same Wi-Fi, or receiving something in the past grants no sharing permission. Resume only with the same authenticated peer and previously approved payload while the approval is active. Allow cancellation and expire approvals. Ask again after revocation, expiration, a change in payload or a new session. Never relay or auto-forward. Every subsequent recipient requires a new approval.

## Content and rights

| Content | What the sender can approve |
| --- | --- |
| Published references, basemaps, place data and routing | Specific editions with known redistribution rights and attribution. Bind those permissions to a verified catalog or signed manifest and digest. The current catalog has sharing disabled for every entry. Establish the first eligible reference and regional bundle with documented provenance before enabling production transfer. |
| Files imported into the library | Offer an individually selected file when its owner is authorized to redistribute it. Ask the sender to supply or confirm provenance and applicable permission for unknown imports. Treat a peer's rights declaration as unverified, and distinguish these items visibly from publisher-verified editions. Keep downloaded assets with known restrictions ineligible. |
| Web sources saved from Ask | Let the sender offer a source on its own, even when the original question stays private. Preview the URL, title, date, attribution and exact snapshot or excerpt. Full text requires permission to redistribute it, including any conditions. Where allowed, offer citation metadata or a permitted excerpt when the full snapshot is ineligible. A successful fetch or an existing local cache entry is no evidence of redistribution rights. |
| Cached questions and answers | Treat as private by default. In Ask, show a preview with independent controls for the question, answer, citations and each eligible source. Allow sender edits or removals before approval, and bind approval to the exported copy. Review provider output and citation terms before enabling each provider, and keep Google Search-grounded Gemini material out of nearby exchange and the shared index under the current terms. |

Keep provider credentials, private household data, and unpublished location or routing history out of automatic discovery and content packaging. Household backups already have their own explicit export path. Preserve original licenses and attribution in received items. New app code remains MIT. [Project license inventory](THIRD-PARTY.md) · [Google Search grounding terms](https://aistudio.google.com/docs/terms#grounding-with-google-search)

## Transfer and offline use

- Add a versioned offer manifest with item kind, digest, byte count, edition, language, map coverage where relevant, provenance, date and license. Use exact content digests for deduplication. Use a signed catalog or pinned publisher digest to establish publisher authenticity. A matching peer-provided hash establishes transfer integrity only.
- Use bounded, resumable chunks over an authenticated encrypted connection. Stage content in app-managed storage, check disk capacity including indexing or extraction, and verify chunks and final digests. Persist completed ranges. Install or replace atomically through existing library and map import paths after format and manifest checks. Reject invalid sizes, path traversal, unsafe URLs, duplicates and unsupported versions. Remove expired partials. Preserve the working edition if verification or indexing fails.
- Import received web snapshots as inert local text and attribution with distinct received provenance. Store received Ask exports separately from the recipient’s own Ask history. Expose both in offline search with tap-through to saved sources. Keep a shared answer visibly attributed and dated, and keep it separate from source evidence when answering another question. Strip active content, block automatic fetches, and retain timestamped publisher references. Add removal and index cleanup.
- Show the vintage and coverage of maps and guidance when offline. Offline routes describe recorded road connections. Bridge closures and emergency notices need separately dated, sourced information. Nearby transfer does not verify whether a bridge or service works now.

## Implementation and release gates

| Slice | Deliverable | Acceptance |
| --- | --- | --- |
| 1. Lightweight build and direct discovery | Measured lightweight release profile, starter reference and a foreground Nearby screen with verified pairing. | Cold install on two physical iPhones, including one on an older supported iOS. Disable cellular, disconnect both from any access point, leave Wi-Fi radios enabled, and demonstrate discovery and pairing. Repeat on a LAN without internet and with local-network permission denied. Verify discovery traffic exposes only the ephemeral service fields. |
| 2. Verified reference transfer | One permitted seed reference, sender and recipient approval, encrypted resumable transfer, atomic install and offline reading. | From fresh launch to the first transferred readable reference in two minutes on a same-room test, as a provisional usability target. Transfer a roughly 1 GB fixture across a drop and relaunch, verify that only missing data is sent, and verify checksum rejection, cancellation, disk limits, duplicate handling and continued usability of the previous edition. Repeat with cellular on and verify no cellular bytes are used for exchange. |
| 3. Useful regional content | A dated, redistributable starter set covering emergency references plus one named map region with places and routing. Large libraries remain individually selectable. | Measure bytes, battery use and indexing delay. Open references, find places and preview routes after an offline cold launch. Demonstrate that a third phone can receive a previously transferred permitted item only after a fresh approval. |
| 4. Sources and Ask | Source-only sharing, editable saved Q&A export, rights enforcement and offline retrieval. | Transfer a permissible sourced answer and a web snapshot between two phones. Find the source with the internet off. Verify that omitted questions, credentials, sources, redacted text and blocked provider material never reach the other phone. Exercise stale citations, malformed input and removal from local search. |

Use deterministic fixtures for manifests, rights policy, consent and resume state. Before public rollout, repeat the device tests across mixed OS versions, locked screens, Low Power Mode, loss of range, and more than two discoverable devices. Review store install size, local networking behavior, licensing and privacy independently of the desktop parity checklist.
